# 04 · 取り込みパイプライン

草案「それぞれのソースの扱い（ソースをアプリ内に保存するための方法）」の実装仕様。
草案の矢印図をそのまま段階（Stage）に落としてある。**草案の段階を省略しないこと。**

---

## 0. 共通フロー

```
追加(D&D / ダイアログ / URL / Studioインポート)
  ↓ ① 受理:  拡張子+マジックバイトで kind 判定 → sources/ にコピー → SHA-256 → 重複検出
  ↓ ② 登録:  sources 行を status='queued' で作成 → UIに即時反映
  ↓ ③ ジョブ投入: ingest ジョブをキューへ（同時実行数は設定値）
  ↓ ④ 解析:  種別ごとのパイプライン（§1〜§9）→ derived/ 生成 → documents 作成
  ↓ ⑤ 正規化: derived/<sid>/document.md を生成（全種別共通の「AIが読める正」）
  ↓ ⑥ チャンク化: §10
  ↓ ⑦ 埋め込み: バッチで chunk_vectors へ
  ↓ ⑧ FTS: chunks_fts + app.db の global_index へ投入
  ↓ ⑨ 完了: status='ready'（AI工程が一部失敗なら 'ready_partial'）
```

### 共通規約

- **各Stageは冪等**。途中で失敗して再実行しても壊れない。`derived/<sid>/` は再実行時に一度削除して作り直す。
- **進捗は Stage 単位で `job://progress` を出す。** `phase` には `"extract" | "ocr" | "vision" | "transcribe" | "chunk" | "embed" | "index"` を入れる。
- **AI呼び出しは全て失敗許容**。失敗したらその情報を欠いたまま先へ進み、`status='ready_partial'` にして再実行可能にする（[`02_アーキテクチャ.md`](02_アーキテクチャ.md) §7）。
- **1ソースの解析は1トランザクションではない**（長すぎる）。Stage単位でコミットし、`jobs` テーブルで再開位置を持つ。
- **上限**：1ファイル 2GB、1プロジェクト 10,000 ソース。超過時は明示エラー。

## 1. 画像（草案 §画像 の実装）

対応：`png, jpg/jpeg, webp, gif, bmp, tif/tiff, heic/heif(任意feature), avif`

### Stage 1-1 形式確認・画像の正規化

- マジックバイトで実形式を確認（拡張子を信用しない）
- EXIF の Orientation を適用して回転を焼き込む
- **カラースペースを sRGB に変換**
- アニメーションGIF/WebP は**先頭フレームのみ**を解析対象にする（明示的にUIへ表示）
- 長辺 2048px を超える場合、Vision入力用に長辺2048pxへ縮小した `derived/<sid>/pages/0001.webp` を作る（原本は保持）
- 極端に細長い画像（アスペクト比 > 4:1、例：長いスクリーンショット）は**縦に重なり付きでタイル分割**し、各タイルを `documents.kind='image'` として別 ordinal で登録する（Vision モデルの解像度制限対策）

### Stage 1-2 Visionモデルによる画像解析

草案が列挙する5項目を**構造化出力で一度に取る**。JSON Schema を `response_format` に渡し、対応していないエンドポイントには「JSONのみで返せ」というシステムプロンプト＋パース失敗時1回リトライで対処。

```jsonc
// derived/<sid>/analysis.json
{
  "ocr": {
    "text": "…",                    // 読み取れた文字（版面順）
    "blocks": [{"text":"…","bbox":[0.1,0.2,0.5,0.3],"lang":"ja"}]
  },
  "entities": [                      // 物体・人物・場面
    {"label":"whiteboard","bbox":[...],"confidence":0.9},
    {"label":"person","count":3}
  ],
  "scene": "会議室でホワイトボードを使った説明",
  "figures": [                       // 図表・グラフの構造
    {"type":"bar_chart","title":"四半期売上","axes":{"x":"四半期","y":"百万円"},
     "series":[{"name":"2025","points":[["Q1",120],["Q2",143]]}],
     "note":"数値は目視推定"}
  ],
  "layout": {                        // レイアウト・位置関係
    "description":"左上にタイトル、中央に図、右下に注記",
    "regions":[{"role":"title","bbox":[...]}]
  },
  "meaning": "この画像は…を示している",   // 画像全体の意味
  "modelUsed": "gpt-4o-mini",
  "degraded": false                   // Vision非対応でOCRのみだった場合 true
}
```

- **Visionモデルが未設定 / 非対応（C-2）の場合**：`degraded=true`。Tesseract OCR があればそれを使い、無ければ「画像（解析なし）」として登録。UIにバッジを出す。
- **図表の数値は必ず「目視推定」と明記させる。** 捏造した数字を確定値として扱わせない（Hallmark の honest-copy 規律と同じ理由）。

### Stage 1-3 検索用インデックス作成

`documents.text` には**検索と回答生成の両方に効く形**で連結して入れる：

```
[画像] <ファイル名>
場面: <scene>
意味: <meaning>
レイアウト: <layout.description>
図表: <figures を1行ずつ自然文化>
本文(OCR): <ocr.text>
```

### Stage 1-4 質問時（検索→回答）

1. ユーザーの質問 → ハイブリッド検索で関連画像・画像領域を取得
2. **元画像＋抽出情報の両方**をVisionモデルへ渡す（草案の明示要件）
   - 画像は base64 data URL で `image_url` パートとして送る
   - 同時に `analysis.json` の要約テキストも渡す
   - 領域が特定できている場合（`{t:"region"}`）、その領域を切り出した画像も追加で送る
3. 回答＋引用（`{t:"region", bbox}`）。UIは画像上に矩形ハイライトを描く

## 2. 音声（草案 §音声 の実装）

対応：`mp3, wav, m4a/aac, flac, ogg/opus`
**動画は §3 で音声に落としてからここへ合流する**（草案「動画は文字起こしして全て音声とする」）。

### Stage 2-1 音声形式の変換・品質確認

- `symphonia` でデコード → `rubato` で **16kHz / mono / f32** にリサンプル（whisper.cpp の要求形式）
- 品質チェック：無音率、クリッピング率、平均RMS。**無音率 > 95% なら「音声が含まれていない可能性」を警告**
- 長さ上限なし。ただし 2時間超はUIに処理時間見積もりを出す

### Stage 2-2 発話区間の検出（VAD）

- Silero VAD（`voice_activity_detector`）で発話区間を抽出
- 前後 200ms のパディングを付ける
- 30秒を超える連続区間は、無音の谷で 30秒以下に分割（whisperのウィンドウに合わせる）
- 無音区間はwhisperに渡さない（**処理時間が大幅に減る**）

### Stage 2-3 自動文字起こし

- `whisper-rs`。モデルは設定で選択（`base / small / medium / large-v2`、既定 `small`）
- パラメータ：`language = auto`（設定で固定も可）、`translate = false`、`token_timestamps = true`、`no_context = false`
- ハードウェアアクセラレーション：macOS = Metal、Windows/Linux = Vulkan（無ければCPU）
- スレッド数 = 論理コア数 - 1（最低1）
- **進捗**：セグメント完了ごとに `job://progress`。長い音声で無反応にしない
- 話者分離（diarization）は **v1.0 では実装しない**。`speaker` フィールドは常に `null`（スキーマだけ先に用意しておく）

### Stage 2-4 文章の整形・分割

whisperの生セグメントはそのままでは読みにくい（句読点欠落、細切れ）。

1. **時間的マージ**：隣接セグメントを、合計 30〜60秒 または 400〜600文字になるまで結合
2. **文境界での整形**：organizer ロールのモデルで句読点付与・明らかな誤変換の修正を行う。
   **原文を必ず残す**：`transcript.json` に `rawText` と `text`（整形後）を両方持つ。整形はAI依存なので、失敗したら `text = rawText`。
3. 整形時のシステムプロンプトは **「句読点と改行のみを補い、語を足さない・消さない」** を厳命する（要約させない）

```jsonc
// derived/<sid>/transcript.json
{
  "model": "small",
  "language": "ja",
  "durationMs": 3612000,
  "segments": [
    {"i":0,"tStart":0.0,"tEnd":42.3,"rawText":"えーと 本日は","text":"えーと、本日は…","confidence":0.87}
  ]
}
```

`transcript.md` は `[00:00:00] 本文` 形式の読み物版。

### Stage 2-5 検索インデックス化

- 1セグメント = 1 `documents` 行（`kind='segment'`, `locator={t:"time",tStart,tEnd}`）
- チャンクはセグメント単位（長すぎる場合のみ分割、§10）

### Stage 2-6 質問時

1. 質問 → 関連する文字起こし部分を検索
2. **テキストとしてモデルへ入力**（草案の明示要件。音声そのものは送らない）
3. 回答＋引用（`{t:"time"}`）。UIは引用クリックで**その時刻から再生**する

## 3. 動画

対応：`mp4, mov, m4v, mkv, webm`

1. `symphonia` で音声トラックを取り出す → **§2 に合流**
2. **キーフレーム抽出（C-8で追加）**：
   - シーン変化検出（連続フレームのヒストグラム差分が閾値超過）で代表フレームを抽出
   - 上限 100 枚 / 動画。最短間隔 5秒
   - 各フレームを `derived/<sid>/pages/NNNN.webp` に保存し、`documents.kind='page'`, `locator={t:"time", tStart, tEnd}` で登録
   - Vision が有効なら §1-2 と同じ解析をかける（スライド共有の録画で特に効く）
   - Vision 無効時はスキップし、フレーム画像だけ保存（Viewerのサムネイル用）
3. Viewerでは**トランスクリプトとキーフレームを同一タイムライン上に並べる**

> 動画そのものの再生は WebView の `<video>` を使う。`asset:` プロトコル経由で原本を参照する（コピーを作らない）。

## 4. PDF・スライド（草案 §PDF・スライド の実装）

対応：`pdf, pptx, ppt(非対応→明示エラー), docx, doc(非対応→明示エラー), odp/odt(v1.0非対応)`

### Stage 4-1 ファイル解析

- PDF：`pdfium-render` で開く。パスワード保護は**パスワード入力ダイアログ**を出す（保存はしない）
- PPTX/DOCX：`zip` + `quick-xml` で OOXML を直接パース

### Stage 4-2 ページ／スライド単位に分離

以降は**1ページ/1スライドごと**に、以下5つを全て行う（草案の5分岐）。

#### ├─ テキスト抽出
- PDF：`pdfium` のテキストAPI。**読み順を復元する**（単純なストリーム順ではなく、テキストブロックのbboxから段組を検出して並べ替える）
- PPTX：シェイプのテキスト + **スピーカーノート**（`notesSlide`）を必ず取る。ノートは `documents.analysis.notes` に入れ、本文にも含める
- DOCX：段落・見出しレベル・表・脚注。**見出し構造を保持**して `documents.kind='section'` で分割（DOCXはページ概念が不安定なため、ページではなく見出しで切る）

#### ├─ OCR
- 抽出テキストの文字数が**ページ画像の面積に対して不自然に少ない**（目安：100文字未満かつ画像が存在する）場合、スキャンPDFと判断してOCRへ回す
- OCR は Vision モデル優先、Tesseract フォールバック（§1-2 と同じ経路）

#### ├─ レイアウト解析
- テキストブロックの bbox から、`title / body / caption / header / footer / figure / table` の役割を推定
- ヒューリスティクス（フォントサイズ・位置・繰り返し）で行い、曖昧な場合のみ Vision に投げる（コスト削減）

#### ├─ 表・グラフ解析
- PDF の表：罫線と文字位置から grid を推定 → `derived/<sid>/tables/p0012_t1.csv` に出力
- グラフ：ラスタなので Vision に投げ、§1-2 の `figures` 形式で構造化
- 抽出した表は **Markdownの表としても `documents.text` に埋め込む**（AIが読みやすい）

#### └─ ページ画像としての視覚解析
- 各ページを **150 DPI 相当・長辺最大2048px** で WebP にラスタライズ → `pages/NNNN.webp`
- PPTX は OOXML からの再現描画が困難なため：
  - LibreOffice が `soffice` としてPATHに存在すれば `--convert-to pdf` で変換してからラスタライズ
  - 無ければ**ページ画像なし**で続行し、UIに「スライド画像の生成にはLibreOfficeが必要です」と1回だけ案内する（インストールを強制しない）
- Vision が有効なら、ページ画像に §1-2 の解析をかけて `analysis` に格納

### Stage 4-3 ページ／スライド単位の検索インデックス

`documents.text` の構成：

```
[<ページ|スライド> N/M] <推定タイトル>
<本文テキスト（読み順復元済み）>

表:
| … |

図表: <figures の自然文化>
ノート: <スピーカーノート>
```

### Stage 4-4 質問時

1. 質問 → 関連ページを検索
2. **抽出テキスト＋ページ画像の両方**をモデルへ入力（草案の明示要件）
   - Vision 非対応なら抽出テキストのみ（degraded 表示）
   - 送るページ画像は最大4枚（トークン制限。設定で変更可）
3. 回答＋引用（`{t:"page", page, bbox?}`）。UIはページ上に矩形ハイライト

## 5. Live Illustrator と取り込みの関係

Live Illustrator は**取り込み時に生成しない**。閲覧時にオンデマンドで生成しキャッシュする（FR-L7）。
理由：取り込み時に全ページ解説を生成すると、100ページPDFで100回のAI呼び出しになりコストと待ち時間が非現実的になる。

ただし**先読み（プリフェッチ）はする**：ユーザーがページNを見ているとき、N+1 の解説をバックグラウンドで1件だけ先行生成する。ページ送りが速いユーザーには効く。設定でオフにできる。

## 6. 表計算（xlsx / xls / csv / tsv）

1. `calamine` で読む（xls も対応）。CSV/TSV は `csv` crate、区切り文字とエンコーディングを自動判定（UTF-8 / Shift_JIS / GB18030 / UTF-16 を BOM とヒューリスティクスで）
2. **シート単位で `documents.kind='sheet'`**
3. ヘッダ行を推定（最初の非空行、型の不一致率から判定）
4. `documents.text` は **Markdownの表**。ただし大きすぎる場合：
   - 500行を超えるシートは、**先頭50行 + 統計サマリ（列名・型・非空率・最小/最大/ユニーク数・代表値）**をテキスト化し、全データは `derived/<sid>/tables/<sheet>.csv` に保持
   - チャンクは「50行ブロック単位」で作り、`locator={t:"cell", sheet, range:"A51:H100"}`
5. 数式は**計算結果の値**を使う（`calamine` のキャッシュ値）。数式そのものも `analysis` に残す

## 7. テキスト系（md / txt / JSON / JSONL / コード）

| 形式 | 分割単位 | locator |
|---|---|---|
| Markdown | 見出し（H1〜H3）単位で `kind='section'`。見出しが無ければ 1500文字ブロック | `{t:"line"}` |
| プレーンテキスト | 空行2連または1500文字 | `{t:"line"}` |
| JSON | ルートが配列なら要素単位、オブジェクトならトップレベルキー単位。深すぎる場合は 100KB ごとに切る | `{t:"path", pointer}` |
| JSONL | 1行 = 1 `documents` 行（ただし1万行超は100行ずつまとめる） | `{t:"line"}` |
| コード | **関数/クラス単位**で分割。tree-sitter を使わず、言語別の簡易ヒューリスティクス（インデント + `fn/def/function/class/impl` 等の行頭パターン）で十分。判定できない言語は80行ブロック | `{t:"line"}` |

- エンコーディング自動判定（`chardetng`）。判定不能なら UTF-8 として読み、不正バイトは置換文字にする
- コードは `documents.analysis.language` に言語を記録し、Viewerのシンタックスハイライトに使う
- **最小行数のファイル（10行未満）でもソースとして登録する**。無視しない

## 8. Webサイトリンク

1. `reqwest` で GET（User-Agent は `WAKARU/1.0`、リダイレクト最大5、タイムアウト30秒）
2. `Content-Type` で分岐：
   - `text/html` → `readability` で本文抽出 → Markdown化
   - `application/pdf` → PDFとして保存し §4 へ
   - 画像 → §1 へ
   - それ以外 → 未対応として明示エラー
3. **取得したHTMLと本文Markdownを `derived/` に保存する**（後でオフラインでも読めるように。I-2）
4. 本文中の画像は取得しない（既定）。設定で「画像も取り込む」をオンにできる（上限20枚）
5. `documents` は見出し単位（§7のMarkdownと同じ扱い）、`locator={t:"anchor", selector}`

**セキュリティ**：
- `file://`, `localhost`, プライベートIP（10/8, 172.16/12, 192.168/16, 169.254/16, ::1 等）への取得は**既定で拒否**（SSRF防止）。設定で明示的に許可できる
- 取得したHTMLをそのままWebViewでレンダリングしない。**必ずMarkdown化してから `react-markdown` で描画**（`rehype-raw` 不使用、[`02_アーキテクチャ.md`](02_アーキテクチャ.md) §1）

## 9. 未対応形式の扱い

未対応の拡張子を投げられたら：
- `status='failed'`, `error_code='SOURCE_UNSUPPORTED_FORMAT'`
- UIには「WAKARUはこの形式に対応していません。PDFに変換してから追加してください」＋対応形式一覧を出す
- **黙って無視しない。リストから消さない。** ユーザーが追加したものは必ず一覧に残す

## 10. チャンク化の規則（全種別共通）

| 項目 | 値 |
|---|---|
| 目標サイズ | **800トークン**（日本語は概ね500〜600文字） |
| 最大サイズ | 1200トークン。超えたら分割 |
| 最小サイズ | 80トークン。下回るものは前後のチャンクへマージ（見出しだけのチャンクを作らない） |
| オーバーラップ | 前チャンク末尾の **15%**（最大120トークン） |
| 分割位置の優先順 | ① 見出し境界 → ② 段落境界（空行） → ③ 文境界（`。．.!?！？` + 閉じ括弧） → ④ 強制文字数 |
| トークン数え | `tiktoken-rs` の `cl100k_base` を近似として使う（正確な一致は求めない） |

### チャンクに必ず付けるヘッダ

検索ヒット時に文脈が失われないよう、**各チャンクのテキスト先頭に来歴を埋め込む**：

```
《<ソース名> / <ページ12> / <推定タイトル>》
<本文>
```

このヘッダは埋め込みにもFTSにも含める。回答時にモデルへ渡すときも残す（引用の精度が上がる）。

## 11. 並行実行とリソース制御

| 種類 | 同時実行数 |
|---|---|
| ingest ジョブ全体 | 設定値（既定 `max(1, cores/2)`） |
| Whisper 実行 | **常に1**（メモリとGPUを食うため直列化） |
| Vision API 呼び出し | 設定値（既定3）。429 を受けたら自動的に半減させ、成功が続いたら戻す |
| 埋め込み（ローカル） | 1（バッチ256） |

**UIの応答性を優先する。** 解析中でも Viewer のページ送り・検索・チャットは待たされてはならない。ジョブワーカーは別 tokio ランタイム（`worker` スレッドプール）で動かし、IPCコマンドのハンドラをブロックしないこと。
